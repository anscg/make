# General

This is **make**, a Hack Club You Ship, We Ship program. Kids build projects, submit them for review, and approved work earns hours toward a grant. A Rails API holds identity, data and the staff/reviewer UI; a Next.js app is the public site.

Keep changes low impact and responses concise. Reference the existing codebase for style consistency. # Layout

```
make/
├── api/        Rails 8 — identity, data, jobs, staff & reviewer UI
├── web/        Next.js 16 — public site, proxies to Rails
```

`bin/setup` once, then `bin/dev` — Rails on :3000, Next on :3001. Postgres must be running; there is no Docker in the local loop. `bin/dev` runs both apps in one process group, so Ctrl-C takes down both.

# Stack

Ruby 3.4.4, Rails 8.1.3, Postgres. Next.js 16.3.4, React 19.2.8, Tailwind 4, TypeScript 5. Only suggest changes applicable to these versions. Prefer CLI-generated boilerplate over manual file creation — you can always modify generated output.

Solid Cache, Queue and Cable back `Rails.cache`, Active Job and Action Cable. In development they share the dev database; in production each needs its own — see the README before touching `cache.yml`/`cable.yml` or `config.solid_queue.connects_to`.

Rails views are ERB; `app/components/` and `app/views/base.rb` are Phlex (`Components::Base`). Analytics is Ahoy, in our own Postgres, never a third party. HCA is Hack Club's unified authentication system and the only way a user signs in — `HCAService` wraps it.

`web/AGENTS.md` is generated by `next dev` and warns that this Next.js version differs from your training data. Heed it: read `node_modules/next/dist/docs/` before writing Next code, and commit the block rather than deleting it from a diff.

# The proxy boundary

**The browser only ever talks to Next.** Rails is not publicly reachable, and `web/lib/rails.ts` is the only path to it. Everything the browser touches is same-origin, so there is no CORS and no cross-site cookie. Preserve that:

- **Rails sets no cookie `Domain`.** The session cookie is host-only. Do not add a `domain:` option.
- **The proxy sets `X-Forwarded-Host`**, so Rails builds redirect URLs on the public host instead of leaking the internal one.
- **Adding a direct browser→Rails path breaks every assumption below.** If something seems to need one, ask first.

## CSRF lives in the proxy

`Api::BaseController` calls `skip_forgery_protection`, because Rails sits behind the proxy on an internal hostname and its own origin check has nothing true to compare against. The check is made one layer out: `proxyToRails` refuses any unsafe method whose `Origin` is not this site, and it is **the only CSRF defence the JSON API has**.

These two facts are one mechanism. Removing the origin check in `web/lib/rails.ts`, or routing around the proxy, leaves the API open. `SameSite=Lax` blocks the same attacks today, but it is a cookie attribute, not a decision.

`verify_proxy!` and `ORIGIN_SECRET` prove a request *arrived through our proxy* — not that a browser meant to send it. Don't confuse the two. The check no-ops when the secret is blank, which is why local dev needs no secret.

`ProxyClientIp` rewrites `REMOTE_ADDR` from `X-Forwarded-Client-Ip`, and only believes that header when `X-Origin-Secret` checks out. Anything recording a visitor's IP depends on this middleware running ahead of `ActionDispatch::RemoteIp`.

# Security & Access Control

## Sessions

Identity lives in the `sessions` table; the cookie carries only an opaque token. `Session.authenticate` is the single read path, and `Session::LIFETIME` is two weeks. This is what makes the console useful — `u.sessions.destroy_all` genuinely kicks someone. Never move identity into the cookie.

## Roles

Three roles in a Postgres array column: `user`, `reviewer`, `admin`. `staff?` is `admin? || reviewer?`. Staff routes sit behind `Constraints::RoleConstraint`, so `/staff/*` is a **404 rather than a 403** for anyone else — a non-staff user learns nothing about what exists there. `Staff::BaseController` repeats the check so a directly dispatched action cannot skip it.

## Pundit

Pundit policies enforce authorization at a low level and should always be used. `ApplicationPolicy` denies everything by default — every permission is opt-in, so a new action that forgets its policy fails closed. Keep it that way. Follow the principle of least privilege, and scope reads through `Scope#resolve` rather than filtering in the controller.

Policies answer *who may*, not *whether it is ready*. `ProjectPolicy#ship?` is permission; `Project#shippable?` is state and belongs in a 422 with a reason, not a blanket 403. Don't collapse the two.

Where a rule protects the audit, enforce it on the **model**, not only the policy, so the console and any later job are bound by it too — `Ship#reviewer_is_not_the_submitter` is the pattern.

## Secrets and PII

`User#hca_access_token` and `Ship#frozen_hca_data` are encrypted at rest. **The access token must never reach a PaperTrail version row** — `User` is versioned on `roles`, `email`, `name` and `slack_id` only, and a test asserts it. If you add a versioned column, check what it would put in the trail.

Production needs `AR_ENCRYPTION_*` keys from `bin/rails db:encryption:init`; development and test derive them from `secret_key_base`. Lose them and every stored token and frozen identity snapshot is unreadable.

Everything passed to the frontend is visible in developer tools. `Serialization` defines one shape per record, shared by the JSON API and the staff UI, so the public site and a reviewer never disagree about what a ship says — add fields there, and check what you are exposing to whom.

## Public IDs

Records expose prefixed hashids (`usr_`, `prj_`, `shp_`) via `PublicIdentifiable`, and `to_param` emits them. **Never expose or accept a raw bigint id** in a URL, an API payload, or a serializer. Look records up with `find_by_public_id!`.

# Ships and the audit trail

A **project** is a thing a kid is making; a **ship** is one submission of that project for review.

The `frozen_*` columns are the point of `Ship`. A reviewer approves *a specific state* of a project, and the kid can keep working the moment it is decided. **Read the frozen copy everywhere a reviewer or an audit looks — never the live project.** Those columns are written once at submit time and never again.

- `Ship.submit!` snapshots under a lock on the project, because `shippable?` stops being true the moment it is read; a partial unique index on pending ships is the backstop.
- `decide!` refuses anything that cannot be audited later: an approval needs hours, a return or rejection needs feedback the kid can act on, either needs a reviewer on record.
- A project is locked against owner edits while it sits in the queue, and becomes shippable again once a decision lands.
- `frozen_hca_data` holds the submitter's HCA identity as it stood at submit time. Grant eligibility is judged against that, not against whatever the account looks like months later.

PaperTrail versions `Ship`, `Project` and `User`, carrying `ip` and `user_agent` alongside `whodunnit`, so a grant approval can be placed as well as attributed. `whodunnit` is the numeric user id, deliberately — a version still points at the right person after a name or email change. Decisions move real hours toward real money; treat the trail as load-bearing, and never write code that edits or destroys version rows.

# Data Handling

Data must be preservable and reversible. `Discardable` is soft delete: records a kid removes stay in the table so a ship that was already reviewed still resolves to its project. When deleting data, always ask whether it should be soft-deleted or permanently destroyed — never assume either. PII may need true deletion; other data may need soft-deletion for auditability. The developer decides each time.

Migrations that rewrite or drop a column holding reviewed state need explicit approval — a frozen snapshot cannot be reconstructed once it is gone.

# Code Quality

Use Rails, Pundit and React best practices. Keep code DRY with concerns, partials and helpers. Follow the ordering the existing models already use: includes/concerns, constants, `has_paper_trail`, associations, enums, encryption, validations, scopes, callbacks, class methods, instance methods (public then private). Minimize database queries (use `includes`, avoid N+1). Use background jobs for long-running tasks. When adding the `private` keyword, verify nothing below is affected — private methods belong at the bottom of the class.

Maintain existing functionality; do not introduce bugs. Before finishing, run `git diff` to review changes, then from `api/`:

```sh
bin/rubocop -f github
bin/brakeman --no-pager
bin/rails test
```

`api/bin/ci` runs the whole suite the way CI does. From `web/`, run `npm run lint` and `npm run build`. Flag unrelated issues but you don't have to fix them.

## Tests

Minitest with fixtures, parallelized across processors. `AuthenticationTestHelper` gives you `sign_in_as`, `create_user(role:)` and `create_project` — it signs in the way the app actually does, with a real `Session` row and a signed cookie carrying the token. Don't stub authentication past it.

Anything touching review decisions, roles, the frozen snapshot, or what lands in a version row needs a test. `test/models/versioning_test.rb` and `test/integration/audit_trail_test.rb` are where those guarantees are pinned.
